# Limited Codex agent continuation: compatibility gate (0.9.0)

Setting: `resumeLimitedCodexAgents` (host-scoped, default on, all workspaces on this host). It works with the daemon restart opt-in off. Code: `server/limited-agents.ts`, wired in `server/handoff-host.ts`; adoption comes from `server/handoff.ts`. Nothing here was run against a real Paseo agent, account or the owner's home.

## What was verified (2026-11-15)

Sources: `@getpaseo/plugin` 0.15.3 and `@getpaseo/client` type definitions in `node_modules` (the contract the plugin is built against) and the checked-in Paseo docs (`research/paseo/docs/hooks.md`, `sdk-agents.md`). Installed app: `/Applications/Paseo.app` is 0.15.4 (`Info.plist`).

| Question | Evidence |
|---|---|
| Hook names | `agent.turn.before` `{agent, turnId}`, `agent.turn.after` `{agent, turnId, outcome}`, `agent.archive.after` `{agent, archivedAt}` (`dist/server/lifecycle.d.ts`). The old `server.on("agent.turn_ended")` names are deprecated aliases, removed after 2027-04-30; the plugin uses `addHook`. Hooks do not wait (`waits: false`). |
| Latest-turn error shape | The hook's `outcome` is `completed`, `failed` with `error: {message, code?}`, or `canceled` with `reason`. The `timeline` field on the event is deprecated and always empty. Timeline items (`type: "error"`) carry no turn ID, so the plugin does not read the timeline at all: it uses the failed outcome of the hook itself, which names exactly one turn. |
| Cancellation ordering | One turn has exactly one outcome, so a limited turn cannot also be `canceled`. A later stop or message is a new turn (`agent.turn.before`) or a `canceled` outcome, and both clear the candidate. |
| Reload / send | `agents.ref(id).reload({requestId})` reopens the session and interrupts a running turn (existing handoff already relies on it). `agents.ref(id).send(text)` sends one message without replaying attachments or tool calls. Both are on the `PaseoApi` the hook context provides; the plugin manifest has no separate permission list. |
| Archive | `agent.archive.after` clears the candidate; the agent list is read with `includeArchived: false`. |

## Positive evidence used

Only Codex agents (`provider === "codex"`), only a `failed` outcome, and only when `error.code` is `usage_limit_reached` or the message **starts with** "You've hit your usage limit" (the real text Codex wrote in `lastError` of a persisted agent, see research/paseo/limited-agents.md). Quotes, prompts, output or a later mention never match. A missing turn ID is ambiguous and ineligible.

## Not verifiable here (fail closed)

1. **The real structured error code.** `usage_limit_reached` is Codex's own name for the condition but was not seen in a live hook payload. The anchored message is the working evidence; if Codex words it differently, no continuation happens.
2. **The installed 0.15.4 bundle itself.** Reading `app.asar` needed a download tool that was denied, so only the SDK types and docs were checked. Behaviour of the 0.15.4 daemon (for example whether an errored agent reports status `error` or `idle`) is unverified. The plugin therefore accepts `idle` or `error` before the reload and requires `idle` and no active turn after it.
3. **Whether `send` after `reload` is allowed for a plugin from a hook on a remote client's session.** The server-side hook context is used, so it does not depend on a desktop or phone being open.

All three are covered by the disposable-agent live gate (testuser, not the owner's accounts): a positively limited turn, a switch with daemon restart, exactly one continuation across two workspaces; a cancelled agent and a second limited account must not loop.

## Algorithm (as implemented)

- **Candidate:** agent ID + turn ID, in memory only, recorded when the limit failure ends a turn and the setting is on. A new turn, cancellation, archive, completion or a user message clears it. Plugin restart loses candidates; history is never scanned.
- **Adoption:** a verified Codex switch with a known identity. Manual switches are keyed by the CLI transaction (`txn:…`), automatic ones by the switch event they follow (and its time). Evidence (research/reviews/codex-switch-incident-2026-11-14.md, 16:55): reloading a Paseo Codex agent starts new app-server processes that re-read `auth.json`, so a Paseo agent adopts the new login by being reloaded; the shared daemon restart matters for terminal TUIs, not for a Paseo agent. The 0.8.1 reload-only handoff relies on the same behaviour. So the plugin's own reload of the limited agent is the adoption step, and **no daemon restart is required** (route 1). A successful daemon restart of the same handoff is not a separate condition any more, it only means the switch was verified (route 2 is the same adoption, reached through the idle-boundary restart). The setting never turns the daemon restart on. A handoff with no switch identity (for example a restart that is merely pending from an unknown switch) is never adopted. A newer adoption supersedes a pending one. A candidate whose limit ended before the switch time is a normal candidate. One whose limit ended at or after it may have hit either login (a Paseo agent still on the old login hits the old limit after an automatic switch; an agent already on the new login hits the new one), so it is **kept, not dropped**, and continued only on evidence: the target's cached status has a fresh, usable reading fetched after the limit ended (headroom, or a usable paid fallback). Otherwise it is logged once as `waiting for the next switch agent=<id>` and tried again on later runs and at the next adopted switch (new key). Re-adopting the same key is a no-op (it keeps the original switch time). User activity, archive, a newer turn, the setting off or the 7-day maximum waiting age (`skipped … reason=waited longer than 7 days`) drop it; a plugin restart loses it (candidates are in memory only). Log lines that were only a one-time "waiting" notice are forgotten with the candidate.
- **Switch target usability:** before the reload, every run reads the target from the CLI's cached `status --json` (windows and `paidUsage`, as the popover does; no model or HTTP call). Mirrors the core (`PolicyEngine`, `PaidUsage.eligible`): *exhausted* = both `codex:primary_window` (5h) and `codex:secondary_window` (7d) present (real Codex status ids are `bucket:window`; `five_hour`/`seven_day` are Claude's), every window of every bucket fresh (not stale, not inferred, not past its reset) and one at 100 or more, and no usable paid fallback (reading under 180 s old; credits with a positive signed balance or unlimited; or enabled extra usage under its limits). Exhausted keeps the candidate waiting (`waiting until the target has headroom or the next switch agent=<id> reason=target exhausted`): it continues as soon as a later run sees headroom or credits, or at the next switch. Headroom or usable credits continue as normal. An unreadable, stale or unknown status (missing window, inferred or stale reading, no matching account) keeps the old behaviour (continue) and logs `target usage unreadable, stale or unknown, continuing anyway` once per switch.
- **One reload per agent per switch (shared ledger):** the handoff and the recovery share one in-memory ledger keyed by the adopted switch (`txn:…` or the event key). Whoever claims an agent first reloads it and records it; the other never reloads it again. Every Codex agent that is not running a turn (idle **or error**, for example stopped by a usage limit) is reloaded once per adopted switch, including parked, waiting, dropped and limited ones; a busy agent is never interrupted, and the handoff reloads it as soon as it is idle. There is no global gate: each Paseo Codex agent has its own app-server, so the non-running agents are reloaded at once and a busy agent never delays them; a running agent has no deadline: it is reloaded whenever it becomes idle, for as long as that switch is the current one. A newer switch (an event, or a request from the plugin) supersedes a handoff that is only waiting to reload running agents (code `superseded`) and reloads every agent under its own ledger key. A candidate whose adoption was overtaken by a newer switch (`login changed`) is parked, not dropped, and continues with the newer adoption. Known windows, accepted: a running agent stays on the old login until its turn ends (the token-rotation risk, see REVIEW-NOTES), and a turn that starts between the per-agent `list()` and `reload()` is interrupted (SDK 0.15.3 cannot block a turn from starting). Only the shared Codex daemon restart (`restartCodexDaemon`) still waits until every Codex agent is idle, because it interrupts all attached sessions. A continuation is sent only after that agent's reload for this switch: the recovery sends without reloading again when the handoff already did, and sends nothing when that reload failed. A restart forgets the ledger.
- **Which setting gates the reload:** a switch made from the plugin (manual) always reloads the non-running agents. A switch made from the app, the CLI or the poller shows up in the event log (checked about once a minute) and is handled as an automatic one: its reload is gated by `reloadCodexAfterAutomaticSwitch` (default on). With that off the handoff reloads nothing and only the recovery reloads the limited agents it continues (gated by `resumeLimitedCodexAgents`). Recovery also runs from the plugin's interval, so a parked candidate is retried when the target's status improves.
- **Accepted limit:** a usable target reading fetched after the limit does not prove the agent hit the old login (Codex can refuse at a server limit while the cached reading shows below 100 %, or on a per-model bucket the check does not tie to the agent). The agent then gets one continuation, hits the limit again and is suppressed; the damage is bounded to one message.
- **Persistence races:** the in-memory state is invalidated synchronously by every hook (new turn, cancellation, archive); every side effect (reload, send) is preceded by a fresh eligibility check made after the previous durable save finished, plus a synchronous identity check with no await in between. The continuation marker is removed again if the send is abandoned.
- **Switch target:** adoption requires the verified switch target (manual: the target; automatic: the `target` of the switch event). An event without a target is never adopted, and the target must be the active login at the idle boundary, not whatever is current later.
- **Same login:** the active Codex account (fresh, cache-only status) must be the switch target at adoption (manual switch) and still the same account right before and right after each reload; if it changed, nothing is reloaded or sent.
- **Per candidate:** recheck latest turn, not busy, `idle`/`error`, still listed (not archived), setting on, login current. The attempt is consumed (persisted) before the reload, so a failed reload or send is never retried for that switch. Reload, recheck (now `idle`), then one message: "Continue the previous task from where it stopped because of the usage limit." At most one attempt per candidate turn and switch. Candidates whose limit ended after the switch are kept and continued only on fresh target evidence (see Adoption and Switch target usability above).
- **No loops:** a continuation we sent is tracked (`lineage`, persisted). If its turn ends in a limit again the agent is suppressed until a turn we did not send (user activity) starts. A completed continuation ends the lineage.
- **State file:** `~/Library/Application Support/SubBaton Paseo/limited-agents-v1.json` (owner-only, atomic, bounded): consumed attempt keys, suppressed agent IDs, lineage. No messages, tokens or prompts. An unreadable file means nothing is recorded or sent.
- Daemon reload of other idle agents (existing handoff) never grants continuation permission.

## Immediate recheck after a Codex limit (0.9.8)

Every positive Codex limit starts one recheck (single flight, at most once per 60 s, a 250 ms collection window per burst): `codex auto run-once --limit-observed <active-account-id> --json`, or a plain `codex auto run-once --json` when no agent of the burst can be on the current login. A switch is adopted from the event log at once and flows through the handoff ledger as usual.

**Which login did the limited agent use?** A Paseo Codex agent keeps the login its app-server started with. The plugin therefore records when each agent's session opened (`agent.open.before`: create, resume, reload; persisted in the recovery state, pruned with the agent) and compares it with the active account's `activatedAt` from the status:

- opened after `activatedAt` and before the limited turn started: on the current login, the flag is sent;
- opened before `activatedAt`: on an old login, never counted (plain run-once, `limitObserved=skipped reason=agent not on the current login`);
- opened after the limited turn started (a reload in the gap before the hook): not the process that ran the turn, never counted;
- unknown (no open record, an unknown turn start, no `activatedAt`): the flag is sent (`recheck attribution unknown, sent (core plausibility gate applies)`); the core ignores it when a recent real reading shows every window under 90 %.

One current or unknown agent in a burst is enough; known-old agents never count. If the CLI does not know the flag (`invalidInput`), the recheck falls back once to a plain run-once.

**Reloads count even if `agent.open.before` does not fire.** A successful reload by the plugin (the handoff's reopen or the recovery's own reload, both through the shared reload ledger) records the agent's open time at the moment the reload finishes (logged as `session opened ... reason=reload`). The later of the two records wins. So attribution does not depend on `reload()` firing `agent.open.before`; the hook still covers agents created, resumed or reloaded by Paseo itself.

**To verify live:** whether a `reload()` also fires `agent.open.before` (reason `refresh` or `resume`). The plugin logs every open in `paseo plugin logs subbaton` (`limited-agents: session opened agent=<8> reason=<...>`), so the owner can see it. Without a record (an agent opened before the plugin started and never reloaded) the agent is "unknown" and the flag is sent; the core's plausibility gate protects a healthy account.

The open time is kept in memory at once and written to the state file in the background; a failing write is logged, never thrown.
